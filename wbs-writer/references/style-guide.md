# WBS 写作规范（以张三《智能问数-周度计划表》为标杆）

## 1. 表结构（固定 8 列，顺序不可变）

| 列 | 写法 | 示例 |
|---|---|---|
| 周期 | `WeekN（MM/DD-MM/DD）`，全角括号，周一到周五 | `Week11（11/02-11/06）` |
| 分类 | 项目内的稳定标签，每周复用同一组词，不要每周换叫法 | `智能问数一期开发`、`智能决策`、`语义服务`、`权限依赖`、`后台产品设计` |
| 事项 | 动宾短语，写目标或成果。有多个子项时，在单元格内换行，用 `1）2）3）` 编号 | `根据0827会议更新后台PRD、线框并形成变更对照` |
| 负责人 | 用姓名，多人之间用英文逗号，本人放在第一位。外部协作方写团队名 | `张三,李四`、`平台团队` |
| 预计完成时间 | 未完成项填承诺日（默认本周五）；已完成项填实际完成日；复盘会那一行填次周一 | `2026-11-06` |
| 状态 | 只能填：`已完成`、`进行中`、`待开始`、`暂停` | |
| 交付物/完成标准 | 可以验证的产物，要有名称、版本号或数量；规划行写“完成标准” | `后台PRD v0.64、页面线框 v0.14`、`卡片/表格PRD、触发机制PRD、Payload示例` |
| 备注 | 只写四类内容：**结论**、**量化结果**、**遗留问题**、**依赖或外部待定事项**。可以为空 | `开发测试：120/120，下周重点为回答质量/准确性修复` |

每周最后一行固定写：分类 `WeekN 复盘及下周启动会（次周一）`，事项 `汇总本期方案、产品设计、开发进度`，交付物 `计划表`，备注写复盘会上确认的事项。

## 2. 颗粒度与信息密度

- **每人每周通常 3～6 行**，含复盘会那一行。参考表中，单人每周通常 2～4 行业务事项。证据不足时宁少勿凑。
- 一行对应**一个可交付的工作包**，不对应一次动作。“开会讨论 PRD”“改 PRD”“评审 PRD”属于同一产出，合并成一行，会议的结论写进备注。
- 只在需要说明依据时写会议日期，格式为 4 位 `MMDD`，例如“根据0827会议…”“0824已评审”“1021沟通完毕”。
- 数字是信息密度的核心：页面数、卡片类型数、测试通过数、版本号。证据里有数字就写，**证据里没有的数字绝对不要编**。
- 备注要写得像给管理层的一句话结论，不写过程流水账。备注有多点时用 `1）2）` 分条，每条不超过 40 字；参考表中长备注最多 4～5 条。
- 没把握的内容不进正文，放到 md 的“待确认”清单。

## 2.1 文风：面向管理层，结果导向

读者是项目管理层，要求一眼看出结论。三列各司其职：

| 列 | 写什么 | 不写什么 |
|---|---|---|
| 事项 | 做了什么、做到什么范围。需要体现工作量时，在这里简短写，例如“补齐执行侧原型（17项缺口）” | 过程描述、工具名 |
| 交付物/完成标准 | 产物名称加版本，**不超过 30 字**，例如“1期PRD定稿版、执行侧原型 v0.6” | 解释性文字，如“逐项记录…及原因”“不以…为标准” |
| 备注 | **结论或对项目的影响**：定了什么、能否进入下一阶段、卡在哪里、依赖谁，例如“PRD定稿，作为开发基线”“流程框架确认可用，启动阶段改为先开户定级” | 过程产物的计数（“含75个截图”“17项已收口”）、自我说明（“完成日待确认”“未核对原文”“脚本模拟不代表真实能力”）、W45/W46 这类回溯标注 |

- 备注最多 3 条，每条不超过 30 字。对结论没有影响的过程产物，一律不写。
- 一切“待确认”“证据不足”“未核实”之类的说明，只写进 md，不写进 xlsx。
- 用词跟随本人的叫法（项目名、模块名来自上一版计划表和 config），不要自造名称。

坏：`1）W45：17项原型缺口补建及文档同步已收口 2）本周交付包已包含PRD正文与75个引用截图 3）完成日待确认`
好：`原型缺口已补齐，可作为开发参照`

## 2.2 md 待确认清单的写法

- 每条是**一句本人能直接回答的问话**，不超过 40 字，不出现 E 编号和推理过程。
  - 好：“智能问数本周有交付吗？”“SOP平台研发评审定在哪天？”
  - 坏：“E321的十项已知差异明细未包含在证据中；E37的团队空间整体验收未获后续完整结论……”
- 最多 6 条，按对 WBS 影响从大到小排列。证据编号和判断依据放在“本周规划”表的证据列里。

## 3. 状态判定

| 状态 | 判定条件 | 备注必须写 |
|---|---|---|
| 已完成 | 证据显示已评审通过、已交付确认或已上线；只是“可演示”“初版可用”不算已完成，写进行中 | 有结论或遗留问题时写上 |
| 进行中 | 有进展，但完成标准没有达到 | 当前完成到哪一步，例如“问答记录基本完成，问答详情还在调整” |
| 待开始 | 本周规划的行，或上周计划了但没有任何动作 | 上周行停留在待开始时，写原因 |
| 暂停 | 因依赖、优先级调整或管理层安排而停止 | **原因必填**，例如“语义层依赖”“根据安排调整” |

上周行如果找不到证据，状态和备注都保留原值，只在 md 里列入待确认清单，**不许改成已完成**。“待确认”不是状态值。

## 4. 好例子（摘自参考表，可作为模仿对象）

```
Week2（08/24-08/28）｜智能问数一期开发｜完善后台管理PRD与线框：
1.根据0824评审会议调整
2.新增语义处理功能
3.根据0827管理层会议梳理调整点｜张三｜2026-08-28｜已完成｜完成后台管理PRD v0.64、页面线框 v0.14；根据0827会议形成后台管理功能调整说明 v0.1｜1）PRD覆盖18个页面/能力项：13个自建页面已细化、5个公共组件复用项
2）后台功能调整项：调整说明已完成，正式 PRD 和线框更新纳入 Week3
```
这行的优点：事项说明了依据和范围；交付物带版本号；备注给出量化数据，并写明剩余工作排到哪一周。

```
Week4（09/07-09/11）｜权限依赖｜权限管理公共组件完成初版后，对齐接口、权限粒度及智能问数接入计划｜张三,王五,李四,平台团队｜2026-09-11｜暂停｜权限组件初版、接口说明、智能问数适配清单｜依赖权限组件初版，待平台团队交付后对齐
```
这行的优点：外部依赖单独成行，暂停状态一眼可见。

```
Week9（10/19-10/23）｜智能问数一期开发｜智能问数流程测试、修复｜李四｜2026-10-23｜已完成｜测试记录、修复清单｜开发测试：120/120，下周重点为回答质量/准确性修复
```
这行的优点：只有一句备注，但同时给了量化结果和下周方向。

## 5. 自检清单（生成后逐项过，不合格就改）

1. 只有 8 列，表头文字和参考表完全一致。
2. 周期格式符合 `WeekN（MM/DD-MM/DD）`，N 和上一版表连续。
3. 有复盘会那一行；业务行没有为凑数拆分或编造。
4. 每个“事项”都是动宾结构，没有“研究了一下”“处理了”“跟进”这类空动词结尾。
5. 每个“已完成”行的交付物都是名词性产物，不是“已完成”“OK”。
6. 每个“暂停”行的备注都写了原因。
7. 所有数字、版本号、日期都能在 evidence.md 里找到原文。
8. 没有工具、环境、个人学习类的行。
9. 上周行一条不少，且“事项”原文未改；状态列只出现四种状态。
10. 负责人一栏只写本人和证据里出现过的人。
11. 每个默认填写的周五日期，都在 md 待确认清单里。
12. 交付物不超过 30 字；备注只有结论或影响，没有过程计数和自我说明；xlsx 里没有“待确认”字样。
13. md 待确认每条都是一句问话，没有 E 编号。
