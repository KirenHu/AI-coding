# WorkTwin 一期边界

更新：2026-11-10（定位调整）。此文件是产品范围的准则；描述目标不等于功能已交付，实际状态见各表。

## 产品定位

WorkTwin 是**个人工作上下文中枢**：从本地项目、钉钉/飞书和各 AI 工具的对话中收集本人授权的工作证据，整理为按项目组织的知识，自动产出**项目进度一览、日报与周报**；同一个后台数据库以只读方式开放给 Claude Code、Codex、dsh 和 ChatGPT，让工作信息不再分散在各个工具里。

知识库是中间层，不是终点。用户可感知的价值来自两类产出：

1. **报告**：项目进度一览、日报、周报草稿，每条结论都能追溯到证据。
2. **上下文**：任何一个 AI 工具都能读到其他工具和 OA 系统里发生过的工作，不需要用户重复交代背景。

用户日常仍使用自己的浏览器、文件管理器、OA 和 AI 工具，不需要迁移到 WorkTwin 内工作。界面主要用于授权来源、维护项目登记、查阅或纠正知识、确认报告草稿和配置接入。

## 成功标准

| 指标 | 含义 |
|---|---|
| 周报草稿人工改动比例 | 草稿到可发送版本之间被修改的内容占比，越低越好 |
| 项目归属准确率 | 进度一览中证据挂到正确项目的比例；误合并单独统计 |
| 每周节省时间 | 与手写日报、周报和整理进度相比节省的时间 |
| 跨工具上下文命中 | 其他 AI 经 MCP 提问时，返回结果被实际采用的比例 |

## 分层架构

| 层 | 职责 | 设计要点 |
|---|---|---|
| 采集 | 各数据源适配器，增量拉取或监听 | AI 编程工具优先通过 hook 实时捕获，其他来源增量同步 |
| 证据 | 保存原始事件、真实发生时间、来源和链接，不改写 | 原始记录与提炼结果分开存放 |
| 理解 | 把证据提炼为观察，再归属到项目，区分决策、进展、风险与待办 | 观察是基本单位，带类型、标题、事实、相关文件和概念；会话结束生成会话摘要 |
| 产出 | 项目进度一览、日报、周报 | 进度对照 WBS 或里程碑计算，结论附证据链接 |
| 开放 | 本地 MCP 与只读查询接口 | 渐进检索：先索引、再时间线、最后取详情，控制上下文消耗；本地常驻后台服务 |

采集与理解层的会话处理参考 [claude-mem](https://github.com/thedotmack/claude-mem) 的设计（hook 捕获、观察结构、会话摘要、三步检索），但不依赖其运行：claude-mem 只覆盖 AI 编程工具，不覆盖 OA 等来源。一期可将本机 claude-mem 数据库作为只读数据源之一。

## 关键决策

1. **项目登记表作为归属锚点。**维护一份轻量项目登记：项目名、别名、关联目录或仓库、钉钉/飞书群、负责人。自动推断只在登记项目中选择归属，不自动发明新项目；无法归属的证据保持隔离并进入“未归属”列表，由用户按需关联。
2. **进度对照目标结构。**“做了什么”来自证据，“进度到哪了”对照 WBS 或里程碑。WBS 由 wbs-writer 等流程维护，WorkTwin 读取并比对。
3. **开放一律只读，默认只返回提炼结果。**MCP 与查询接口不提供写入能力；默认返回知识与证据链接，读取原始对话需单独授权。OA 群消息含他人内容，一期只采听记、日程、待办和本人文档，不采群聊全文。
4. **报告由用户确认后自行发送。**WorkTwin 生成草稿，不自动对外发送。

## 知识整理的必要约束

- 业务项目与目录分别记录。一个项目可以跨目录、跨工具；一个目录或会话也可能包含多个项目。目录名不直接决定业务归属。同名项目也不凭名字自动合并。无法判断时按来源/会话隔离；项目关系人工确认仅作为可选的纠错路径，不是日常必经步骤。
- 项目判断优先采用用户明确的项目与目标，结合会话关系、相关资料、仓库和操作记录。时间接近、名称相同或语义相似只能辅助判断，不能单独决定合并。
- 无法确认业务项目的会话和文件，先限制在单份资料；不得凭目录名把其他文件合并，也不得自动当成全局规则。旧版由目录名形成的未经确认项目关联在升级时收窄为单份资料范围；当所有有效证据均来自一份授权文件时，可自动解除 1.1.7 遗留隔离。多文档关系未经确认时仍保持隔离，不生成强制核对任务。跨会话自动识别尚未完成。
- 分析输入应包含当前工作目标、相关双向讨论、实际事件时间、文件与操作线索、已有主题的当前版本、适用范围及来源。工具事件是独立角色，不能归到前后相邻的用户或 AI 发言中；进程退出码为 0 也不是成果验收，通过与否只按实际证据判断。分批处理需保留前后文，不逐条孤立分析用户消息。
- “同意”必须能够对应此前明确的方案。AI 建议、用户确认、AI 报告完成、工具执行依据和用户验收分别记录。单纯“完成了”不能证明成果已验证。
- 同项目、同主题、同适用范围的内容优先更新已有文章，保留理由、例外、未决问题与来源。当前笔记只保留最新有效结论；被替代正文只存在版本历史或更新日志，不另建为有效知识，也不继续混入当前正文。不同主题、不同权限或未解决的矛盾不直接合并。
- 依据来源真实事件时间判断先后；扫描、导入时间不能替代决策时间。同一文件被实际改写且旧引用全部消失，可以把当前文件版本视为后继资料；不得凭文件夹相似就覆盖另一资料的知识。新建议即便更晚也不能推翻用户已确认的结论。
- “用户倾向于第二点”、无对象的泛泛评价、临时回应等不进入供 AI 使用的知识。条目必须能够说明未来可用于回答什么工作问题。
- 术语区分：被替代版本属于历史记录；早期程序提炼但范围、价值尚未核实的结果属于待核对资料，两者不能统称“旧知识”。无有效来源或无法确定结论的结果保持隔离并暂不参与回答；同一份原文件、所有证据均有效且来源授权不变的旧版误隔离结果可以自动恢复，不扩大项目范围或分身授权。
- 原始日志保留为依据；知识库保存可复用内容。MCP 默认检索当前有效知识，需要追溯时再读取允许提供的依据，不能把所有历史讨论直接塞入上下文。

## 交互与验收

知识组织参考 Obsidian：以可独立阅读和编辑的 Markdown 笔记为主体，用双向链接表达主题关系，用少量属性表示项目、主题、适用范围、状态和来源。项目与主题提供导航，不要求用户先设计严密的文件夹层级。来源日志与主题笔记分开，同一主题持续维护当前内容与历史。关系图作为后续辅助视图，不代替笔记正文与证据，也不负责决定权限和项目归属。

Obsidian 只作为部分优秀思路的参考，不以复刻界面、直接接入或双向同步为目标。一期继续使用现有存储与编辑方式，保留已有 Markdown 导出。MCP 按需读取当前笔记、范围和必要引用。

设置固定在主导航底部，长列表由内容区滚动，小窗口下仍可直接点击。条目展示主题、所属范围、适用条件、有效状态与来源；用户可以修改、停用、查看历史。日常采集、更新和清理由后台持续完成，状态区分排队、处理中、失败和确实需要介入的例外，不把每份资料的项目归属当作必须确认的待办。

2026-10-10 调整原则：自动维护的优先级高于逐条人工审核。在已授权数据源内，有可验证原文和明确归因的知识默认自动进入私人知识库；无冲突补充自动应用，可靠后继结论自动替代，原文和历史可追溯。无法确认项目时缩小适用范围，而非要求用户选择项目。真实资料验收和持续质量评测仍必须开展，但不再成为每条私人知识自动生效的交互性前置条件。重大跨来源矛盾、人工修正被覆盖、分身权限扩大等不自动批准；AI 生效不等于用户亲自确认。

MCP 直接沿用数字分身已保存的知识授权，不复制一套权限。每个分身可生成、更新或关闭独立连接凭据；每次读取都检查当前授权和知识有效状态。只提供项目列表、检索、当前笔记和必要引用，不提供知识修改能力。完整日志默认关闭，需在分身配置中单独授权，且仅限当前授权知识引用的来源资料。撤权、停用、删除分身或关闭 MCP 立即停止读取。

验收必须覆盖：设置在长列表下可见；局部英文提示词要求不能成为所有项目的规则；同主题更新保持原文档编号与历史；冲突未解决时不混入有效知识；未授权来源不进入分析；其他 AI 经 MCP 能读取对应项目的当前知识。完整日志归属、真实资料质量和打包客户端接入尚未通过时，不能宣称一期核心闭环已经完成。

## 个人与企业配置

个人自行配置模型地址、模型与 Key。企业统一分配模型，员工使用企业 Token，不接触供应商 Key。两者共用采集与知识整理逻辑，数据使用与分享遵守来源授权。

现有“数字分身”、远程分享和企业管理员功能保留兼容，但不再作为此次核心范围扩建。是否收敛入口应围绕 MCP 访问与知识授权设计，不继续追加秘书能力。

Apple 签名、公证与自动升级不影响上述能力定义。合成资料和模拟模型测试不代表真实知识质量已通过验收。
