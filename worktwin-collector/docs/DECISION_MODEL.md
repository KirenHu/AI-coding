# WorkTwin · 项目判断模型与分身动态授权（1.1.9 草案）

## 设计目标

- 用户只配置采集范围、主模型，以及可选的项目判断模型。不再逐份确认项目归属，也不在每次产生知识后重新勾选分身。
- 主模型阅读原始资料，提取主题、具体项目线索与可复用知识；判断模型只做有限选项的匹配/冲突裁决。Jev 是 SystemOne typed decision API，不能作为 Chat Completions LLM。
- 判断和知识操作分开：ProjectMembership 的关系不能越权授权来源，TwinGrant 也不由 AI 自动创建。

## 判断模型配置

个人版：设置 →「项目归属判断模型（可选）」→ 选“主模型”、“Jev · SystemOne”或“其他 Chat Completions”。Jev 的官方 API 根地址可填 `https://api.typesafe.ai`，模型名 `jev-latest`。也可填写实际购买的 Jev 托管服务地址，必须提供其 `/v1/systemone` 端点。Key 保存在 OS 钥匙串或本地加密文件，不随知识备份导出。连接测试使用合成状态，不发送真实工作资料。

企业版：管理员设置 →「专用判断模型」。Key 仅存于企业服务端的加密存储；员工只能调用企业服务受限的 `/v1/decisions`。企业服务按 Token 权限校验和每用户每分钟调用数限制。员工无法获取供应商 Key。

不配置判断模型时使用当前主模型；已配置专用判断模型时优先处理项目匹配，失败则回退主模型；输入只包含相关工作单元和候选项目的有限摘要，不发送全部文件或会话。

## 知识组织与归属

- 以单条提取结果作为一期的 Work Unit，保留证据原文 Hash、主题、项目提示、判断状态、置信度和来源文档 ID。
- 一个来源文档可包含多个 Work Unit，各自有独立 ProjectMembership。
- 先依据来源明确提及的项目名称建立或查找项目；已存在候选时结合特定工作单元的代码仓库或 PR 线索与当前有效的项目知识，请判断模型裁决。
- 无可靠项目提示、候选冲突、判断低置信度：保持 Session 作用域，不要求用户审核，也不得扩大共享范围。
- 项目列表有稳定身份，不因目录名相同就合并；同一仓库也可能对应多个业务项目。
- 当前实现着重在新工作单元进入知识库时进行匹配；持续自动复查旧项目关系、跨来源冲突复原和大规模误合并分析需进一步验证。

## 数字分身知识授权

`TwinGrant` 支持 `project`、`source`、`global`、`knowledge` 四种授权目标和 `allow/deny`。已有 `twin_knowledge` 逐条授权作为兼容的显式选中项。

- 新建分身默认动态模式，但在用户真正授予项目或来源前，不会自动看到未选知识；旧分身升级后维持手动模式。
- 项目授权自动包含该项目后续新增的有效知识；来源授权在同一文章包含多个来源时要求全部来源均已授予。
- 规则中的拒绝优先于允许；撤销来源 AI 权限、来源文件删除、知识失效将立即从本地问答/MCP 的可用结果中排除。
- 远程发布还需原始来源的 `allow_share` 授权。Remote snapshot 在本地 WorkTwin 运行且联机时持续同步；本地离线时远程只能读取最后一次成功同步的授权版本，紧急撤权应从企业服务端处理。
- 自动项目识别不创建 TwinGrant，不覆盖手动排除或手动编辑成果。

## 验收与后续

本 PR 为叠加在 1.1.8 自动知识维护草案上的独立开发分支，不是正式发布包。必须通过单元测试、浏览器验收、macOS/Windows 打包验收与本人真实项目资料样本再决定合并和发布。

优先看四个指标：自动识别项目的覆盖率、误合并率、分身自动继承准确率、每百次知识更新的人工介入次数。独立判断模型带来的成本/延迟收益应在同一数据集上与主模型对比，不宣称未经测量的实际节省值。


## 混合资料与撤权保护

对同一份会话/文档中的多个项目，完整来源日志可能含有某个分身未授权的其它工作内容。因此，混合项目资料的完整日志必须同时满足：单独开启日志访问；为该分身显式授权整个来源；没有项目、知识或来源的排除规则。仅得到单个项目的知识授权不能直接读取整份混合原始日志。撤销 AI 授权后，历史项目名称不再进入判断模型候选列表。
